## 1. 问题

### R-H07 — 恢复归档无路径规范化（High / Security）

`app/ops/backup.py` 的 `_extract_artifacts` 仅检查 `arcname` 以 `articles/` 开头：

```python
rel = arcname[len(prefix):]      # "articles/../escaped.txt" -> "../escaped.txt"
dest = staging / rel             # -> 写到 staging 的父目录
```

未拒绝 `..`、绝对路径，也未校验最终 resolved path 的归属，`dest = staging / rel`
可越过 `data_dir`，以恢复进程权限覆盖其他文件。审计复现：`articles/../escaped.txt`
通过 `validate_archive`，恢复写到 articles/staging 之外。

### R-M01 — 恢复先覆盖在线文件，DB 失败后无法回滚文件（Medium）

`_extract_artifacts` 在**检查 image rows 和导入数据库之前**就把 staging 文件移入
live。随后缺图片或 DB 约束错误只能回滚 DB，旧文件已被替换。审计复现：临时 live
文件为 `ORIGINAL`、备份为 `REPLACED`、归档 DB 行含无效必填字段，restore 报
`IntegrityError` 后文件仍为 `REPLACED`。

### R-M02 — 付费服务成本随 reset/重生成丢失（Medium）

已修：DataForSEO `cost` 字段、LLM usage append-only、有效图片复用零新增。
未修：SERP 重试删除 `serp_runs`（含 cost）；图片重新规划删除 `images`（含 cost）；
同图坏文件重生成覆盖旧 `provider_cost`；证据核实额外抓取没有保存 `ExtractedPage`
成本；共享 `source_pages` 行无法表示每次 job 的实际花费。

## 2. 修复设计

### 2.1 R-H07：任何写入前的规范化 + containment

```python
def _artifact_rel_parts(arcname) -> tuple[str, ...]:
    # 拒绝: 空/NUL、绝对路径(/, C:, \\\\host)、非 "articles" 根、
    #       每个组件为 ""/"."/".."、含 ":" 的组件
    # 返回: articles/ 之下的相对组件
```

- `validate_archive()` 对 **inner tar 的每个 member** 调用它，并拒绝
  symlink/hardlink member → 非法归档在**零写入**前失败。
- `_assert_within(path, root)`：materialize 前后各做一次 `resolve()` containment
  （纵深防御）。
- `_iter_artifact_files()` / `_stage_artifacts()` 复用同一检查 —— 覆盖**实际写入
  流程**，而不仅是 manifest 预览。

### 2.2 R-M01：暂存 → 校验 → 发布(带快照) → DB → 补偿

```
1. validate_archive(archive)                     # 路径/member 安全，零写入
2. stage 到 {data_dir}/.restore_staging          # live 完全不动
3. 归档 image 行逐条对照 staging 校验齐全         # 缺失 -> BackupError，live+DB 不动
4. _promote_artifacts():                         # 覆盖前先把旧文件移入
   旧 live 文件 -> {data_dir}/.restore_rollback   #   .restore_rollback 快照
   新文件 -> live
5. DB 事务（single commit）
   失败 -> _compensate_artifacts(): 删除新文件 + 快照移回
6. finally 清理 staging / rollback
```

由此：

| 失败点 | DB | 文件 |
|---|---|---|
| 归档非法 / 图片缺失 | 原样 | 原样（未发布） |
| 发布中途失败 | 原样 | 补偿回原样 |
| DB 提交失败 | 原样 | 补偿回原样 |

### 2.3 R-M02：独立追加式付费成本台账

新表 `provider_cost_events`（迁移 `0014`）：

```
id / job_id / provider / step / kind / amount NUMERIC(12,6) NULL / detail / created_at
```

- `kind`：`charged`（付费调用）｜`cache_hit`（命中缓存，0 成本）｜`reused`（复用本地
  产物，0 成本）。
- `amount = NULL` 表示 provider 未报成本（未知 ≠ 0）。
- 服务层 `app/services/cost_ledger.py`：`record_provider_cost` / `record_cache_hit`
  / `record_reuse` / `total_cost`。

埋点（全部在**真实步骤**内，随步骤 checkpoint 一起提交）：

| 步骤 | 事件 |
|---|---|
| `serp_search` | 每次真实 SERP 调用 → `charged`（即使随后 reset 删除 `serp_runs`） |
| `source_extract` | fresh 抽取 → `charged`；TTL 命中 → `cache_hit`（0） |
| `evidence_research` | 独立核实抓取经 `verify_evidence_sources(on_extraction=...)` → `charged` |
| `image_generate` | 重新生成 → `charged`；有效文件复用 → `reused`（0） |

- `checkpoints.reset_from_step` 明确**不删**台账（与 LLM usage 同策略）。
- `cleanup` 把台账列为 job-owned 行，随 job 一起清理（无孤儿）。
- 不新增财务面板（符合审计"不要求增加财务面板"）。
