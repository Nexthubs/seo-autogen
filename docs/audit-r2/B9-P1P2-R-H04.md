# B9 / P1–P2 — R-H04：Provider `raw` 类型与脱敏合同修复

> 所属轮次：第二轮 CODEX Audit 修复
> 阶段：P1（Provider Interface）/ P2（DataForSEO + Source Extraction）
> 关联：旧 M10（脱敏）、M11（error_raw 持久化）——本轮为"修复引入的新集成问题"
> 状态：✅ 完成

## 1. 问题

审计复现：

```
DataForSEO 业务错误携带 dict raw → 编排器失败处理
脱敏报 TypeError: expected string or bytes-like object, got 'dict'
回滚后没有持久化 error code/raw
```

- 位置：`app/providers/serp/dataforseo.py:252–281`、`:364`；
  `app/providers/extractor/exa.py:231`；`app/pipeline/orchestrator.py:454–468`；
  `app/core/redaction.py:131–138`。
- Spec：§49 / §52 / P9 要求保留 raw、稳定错误码、错误可见及可恢复。

### 根因链

1. `PipelineError.raw` 注解是 `str | None`，但 dataclass **不做运行时类型校验**，
   Provider 很自然地传入整个响应 dict（DataForSEO envelope / Exa body）。
2. 编排器失败分支 `job.error_raw = redact(error.raw)` 调用的是**只接受字符串**
   的 `redact()`（内部执行 `re.sub`）。
3. `TypeError` 在 `except PipelineError` 块**内部**抛出，不会被同层后面的
   `except Exception` 捕获（该子句只在 try 体中生效），因此**绕过 commit**，
   job 停留在上一个 status（如 `keyword_preparing`），`error_code`/`error_raw`
   均为空。原本的业务失败被"错误处理器崩溃"彻底吞掉。

## 2. 修复设计

采用审计给出的第一种方案："**明确 raw 的统一类型**；结构化 payload 递归脱敏后
JSON 序列化"，并把归一化放在**单一收敛点**，而不是逐个 Provider 打补丁。

```
Provider 传 dict  ──►  PipelineError.__post_init__
                            │  redact_raw(value)
                            ▼
                   总为 str: 递归脱敏 + json.dumps + 截断
                            │
                            ▼
            ┌───────────────┴───────────────┐
            ▼                               ▼
  orchestrator: redact_raw(error.raw)   DB: generation_jobs.error_raw (TEXT)
  （纵深防御，即使绕过构造函数）
```

### 2.1 `app/core/redaction.py` — 新增 `redact_raw`

| 输入 | 输出 |
|---|---|
| `None` | `None` |
| `str` | `redact(str)`（Bearer / KV / JSON-key / URL-query 全谱脱敏） |
| dict / list / 任意 JSON 结构 | `redact_value()` 递归脱敏 → `json.dumps(..., ensure_ascii=False, default=str)` |
| 不可序列化对象 | `str(value)` 回退后脱敏（永不再抛异常） |

- `RAW_MAX_CHARS = 20000`：`generation_jobs.error_raw` 是调试辅助，不是原始归档
  （完整 payload 按 spec §12.2 存在 `serp_runs.raw_response` JSONB），因此截断并
  追加 `...[truncated N chars]` 标记，避免超大 blob 进 DB / Web UI。
- 保证**幂等**且**绝不抛异常**：失败处理路径本身必须可靠。

### 2.2 `app/core/exceptions.py` — 构造期强制合同

```python
def __post_init__(self) -> None:
    self.raw = redact_raw(self.raw)
```

所有 Provider（现有与未来）无需记忆"raw 必须字符串"，合同由 dataclass 统一保证。

### 2.3 `app/pipeline/orchestrator.py` — 纵深防御

`job.error_raw = redact_raw(error.raw)`。即使有代码绕过构造函数直接
`error.raw = {...}`（例如旧的对象反序列化、第三方子类），失败分支也不会再崩。

### 2.4 `app/pipeline/steps/source_extract.py` — 不丢 Provider 细节

原实现按 URL 吞掉 `PipelineError` 后，最终只抛一条无 raw 的
`SOURCE_EMPTY("no competitor sources could be extracted")`，Exa 的响应体完全丢失。
现记录**最后一次**每-URL 失败的 `raw`，并挂到最终 `SOURCE_EMPTY` 上
（已是脱敏字符串），使"所有来源都失败"时仍能看到 Provider 侧原始诊断。
